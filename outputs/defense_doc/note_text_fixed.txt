Актуальность дипломного проекта обусловлена тем, что в условиях стремительного роста объемов цифровой коммуникации и повсеместного распространения удаленного взаимодействия особую значимость приобретают современные платформы для обмена сообщениями. Современные веб-приложения, ориентированные на организацию групповой и личной переписки, позволяют автоматизировать ключевые процессы: аутентификацию пользователей, хранение и доставку сообщений, управление правами доступа и модерацию контента. Подобный функционал реализуется с помощью современных веб-технологий, где обработка данных распределяется между клиентской и серверной частью, а взаимодействие осуществляется через HTTP-протокол и WebSocket-соединения, обеспечивая стабильную, отказоустойчивую и доступную работу платформы.
Тема дипломного проекта актуальна, потому что внедрение подобного решения значительно упростит организацию цифрового взаимодействия между пользователями, минимизирует зависимость от сторонних платформ и сделает процесс общения управляемым и безопасным для всех участников.
Целью дипломного проекта является разработка веб-приложения для видео-звонков – современной платформы для обмена сообщениями с поддержкой групповых чатов, системы друзей и ролевой модерации. Целевая аудитория веб-приложения включает широкий круг пользователей, заинтересованных в удобном, безопасном и стабильном цифровом общении. Гибкая архитектура разрабатываемого веб-приложения позволит легко масштабировать его функционал и интегрировать новые инструменты по мере роста потребностей аудитории. Таким образом, проект предлагает не просто базовый инструмент связи, а перспективную платформу, отвечающую высоким стандартам отказоустойчивости и качества пользовательского опыта.

Для разработки программного решения необходимо проанализировать существующие аналоги, выявить их достоинства и недостатки, а также ключевые особенности. На основе анализа формируются задачи для разработки программного средства.
1.1 Аналитический обзор аналогов
Для создания приложения с привлекательным пользовательским интерфейсом и удобной функциональностью необходимо проанализировать аналоги. Анализ конкурентов способствует не только выявлению достоинств и недостатков, но также помогает понять, к чему стоит стремиться при разработке собственного приложения и выявить основные потребности всех пользователей веб-приложения.
1.1.1 Аналог «Zoom»
Zoom [1] – это одна из самых популярных платформ для проведения видеоконференций, вебинаров и онлайн-встреч. Сервис завоевал популярность благодаря высокому качеству связи и стабильности работы даже при большом количестве участников. Главная страница приложения, представленная на рисунке 1.1, ориентирована на быстрый старт: пользователь может мгновенно организовать конференцию или присоединиться к существующей.
Рисунок 1.1 – Главная страница веб-приложения «Zoom»
Справа располагается информационная панель, отображающая текущее время, дату и список ближайших запланированных встреч. Навигация по дополнительным разделам вынесена в отдельную панель, что обеспечивает быстрый доступ к истории взаимодействий и адресной книге. Дизайн выполнен в минималистичном стиле, что снижает когнитивную нагрузку на пользователя.
Zoom уделяет большое внимание политике безопасности и условиях использования сервиса, что видно на примере этапа начала видеозвонка, представленного на рисунке 1.2.
Рисунок 1.2 – Принятия условий использования и политики безопасности
Интерфейс активной видеоконференции, изображенный на рисунке 1.3, специально спроектирован таким образом, чтобы максимизировать полезное пространство для видеопотоков участников. Основную часть рабочего экрана занимает динамическая сетка с изображениями собеседников или область демонстрации контента.
Рисунок 1.3 – Окно видеоконференции Zoom
Панель управления функционалом вынесена в нижнюю часть окна и логически разделена на функциональные блоки. В левой части сгруппированы настройки оборудования: управление микрофоном и камерой, позволяющие оперативно включать или отключать передачу сигнала, а также выбирать устройства ввода-вывода.
Важной особенностью организации связи в Zoom является система безопасности и доступа. Как показано в информационном блоке на рисунке 1.4, вход в комнату осуществляется по уникальному идентификатору нужной конференции и коду доступа. Это позволяет организатору четко контролировать состав участников и предотвращать несанкционированное подключение, передавая данные для входа только доверенным лицам.
Рисунок 1.4 – Страница с настройками видеозвонка
Главными плюсами Zoom являются высокое качество связи и широкий функционал для совместной работы, включая демонстрацию экрана и управление участниками. Система безопасности с использованием уникальных идентификаторов и кодов доступа гарантирует конфиденциальность встреч, а расположение элементов управления на главной панели интуитивно понятно.
С другой стороны, Zoom является сугубо корпоративным инструментом для видеоконференций: платформа не поддерживает постоянные текстовые чаты с историей, реакциями, ответами на сообщения и упоминаниями, отсутствует система дружбы и личных переписок, а также невозможно создать закрытое сообщество с регистрацией по инвайт-кодам. Все коммуникации сводятся к временным сессиям, после завершения которых контекст общения полностью и безвозвратно теряется.
1.1.2 Аналог «Discord»
Discord [2] – это кроссплатформенная система мгновенного обмена сообщениями с поддержкой VoIP и видеоконференций, изначально ориентированная на сообщества геймеров, но впоследствии ставшая универсальным инструментом для коммуникации различных групп по интересам.
Организация рабочего пространства в Discord, представленная на рисунке 1.5, принципиально отличается от классических мессенджеров. Основной структурной единицей является «сервер» – изолированное пространство для сообщества. Слева расположена панель навигации по серверам, выполненная в виде вертикальной ленты иконок, что позволяет пользователю быстро переключаться между различными контекстами общения. Интерфейс серверов делится на тематические текстовые и голосовые каналы.
Дальнейшая организация коммуникации внутри каждого сервера осуществляется посредством специализированных каналов, которые сгруппированы по логическим категориям.
Рисунок 1.5 – Главная страница веб-сайта «Discord»
Внутри выбранного сервера пространство разделено на текстовые и голосовые каналы. Текстовые каналы используются для асинхронного обмена сообщениями и файлами, в то время как голосовые каналы (Voice Channels) реализуют концепцию «постоянной комнаты»: пользователь может войти в канал и сразу начать общение без необходимости совершать вызов. Такое архитектурное решение способствует созданию эффекта присутствия. На рисунке 1.6 продемонстрирована страница с пользовательским сервером.
Рисунок 1.6 – Страница пользовательского сервера
Режим видеосвязи в Discord, показанный на рисунке 1.7, активируется внутри голосового канала или в личных сообщениях. Интерфейс звонка поддерживает одновременное отображение веб-камер участников и демонстрацию их собственных экранов.
Центральная область динамически масштабируется в зависимости от количества активных потоков. Характерной важной особенностью является возможность индивидуальной настройки громкости для каждого участника, что решает распространенную проблему разного уровня звука у собеседников. Элементы управления (включение камеры, микрофона, демонстрации экрана) расположены в нижней части и имеют интуитивно понятные пиктограммы.
Рисунок 1.7 – Режим звонка пользователя на сервере
Главными плюсами Discord являются гибкая система организации сообществ через серверы и каналы, а также высокое качество голосовой связи с низкой задержкой и функцией шумоподавления. Возможность находиться в голосовом канале в фоновом режиме делает сервис идеальным для длительного совместного времяпрепровождения.
С другой стороны, Discord не предоставляет инструментов для тонкого управления участниками на уровне отдельного чата: назначить модератора или доверенного участника внутри конкретной беседы невозможно – права действуют только глобально на весь сервер. Кроме того, платформа не поддерживает запланированные сообщения, сообщения с автоудалением, встроенный экспорт истории переписки и подтверждения прочтения, что ограничивает ее применимость в структурированных рабочих коммуникациях.
1.1.3 Аналог «Google Meet»
Google Meet [3] – это сервис видеотелефонной связи, разработанный компанией Google. Это яркий пример полностью веб-ориентированного решения (Web-first), которое не требует обязательной установки десктопного приложения для полноценной работы, что делает его максимально доступным для широкого круга пользователей.
В левой части экрана расположены функциональные кнопки: «Новая встреча», позволяющая мгновенно создать ссылку для приглашения, и поле ввода кода или ссылки для входа. Правая часть страницы динамически интегрируется с Google Календарем, отображая запланированные на сегодня мероприятия. Такое решение позволяет пользователю одним кликом присоединиться к выбранному пользователем совещанию, минуя этапы поиска ссылок в почте или мессенджерах.
Главная страница сервиса, представленная на рисунке 1.8, отличается выраженным минимализмом и отсутствием лишних декоративных элементов. Основное внимание сосредоточено на двух действиях: создании новой встречи и подключении к существующей по коду.
Рисунок 1.8 – Главная страница встречи
Интерфейс самой видеовстречи, представленный на рисунке 1.9 спроектирован с упором на максимальное использование экранного пространства для видеопотоков или демонстрируемого контента. Элементы управления скрываются при бездействии или компактно располагаются в нижней панели.
Нижняя панель инструментов содержит кнопки управления микрофоном и камерой, функцию «Поднять руку» для упорядочивания дискуссии, управление демонстрацией экрана и кнопку завершения звонка. В правом нижнем углу находятся инструменты для доступа к списку участников, текстовому чату и интерактивным активностям (доски, опросы).
Рисунок 1.9 – Режим видеовстречи
Главным преимуществом Google Meet является его доступность: сервис работает непосредственно в браузере, не требуя установки дополнительного ПО на устройства пользователей, что снижает порог входа для новых участников. Глубокая интеграция с экосистемой Google и его сервисами, такими как Календарь, Почта и Диск, делает его идеальным инструментом для корпоративных коммуникаций и планирования.
К недостаткам можно отнести зависимость от учетной записи Google для организации встреч, а также менее развитый функционал текстового чата по сравнению с мессенджерами.
1.2 Патентный поиск
Патентный поиск – это систематический процесс отбора соответствующих запросу документов или сведений по одному или нескольким признакам из массива патентных документов или данных, при этом осуществляется процесс поиска из множества документов и текстов только тех, которые соответствуют теме или предмету запроса.
Патентный поиск осуществляется посредством информационно-поисковой системы и выполняется вручную или с использованием соответствующих компьютерных программ и с привлечением соответствующих экспертов.
Патентный поиск проводился на с помощью сайта Федерального института промышленной собственности [4].
1.2.1 Способ и устройство для обработки видеозвонка
В данной работе был найден патент. Номер заявки 2024103549, дата подачи 17.08.2022 года. Выдан патент № 2 851 521. На данный патент имеет право БИГО ТЕКНОЛОДЖИ ПТЕ. ЛТД. (Сингапур). Авторы изобретения: СЯ Юньчан (CN), ДЭН Юн (CN). МПК: H04N 7/14 (2006.01). Дата публикации заявки: 12.04.2024, Бюл. № 11.
Изобретение относится к области обработки видеозвонков в системах групповой видеосвязи с использованием серверной переадресации потоков. Способ предусматривает определение битовой скорости слоя для каждого слоя кадра в видеоданных, отправленных передатчиком, при этом видеокадры организованы в иерархические слои на основании отношения зависимости между ними. На основании измеренных пропускных способностей восходящих каналов каждого из получателей и общей пропускной способности нисходящего канала сервер динамически выделяет каждому получателю индивидуальную полосу пропускания. Для каждого получателя определяется целевой слой кадра, соответствующий его пропускной способности, после чего сервер переадресует видеоданные с применением алгоритма выборочного извлечения кадров на основе динамически управляемых порогов байтов. Изобретение направлено на обеспечение качества передачи видео при групповых звонках в условиях ограниченной пропускной способности.
Данное техническое решение представляет особый интерес для разрабатываемой системы, так как позволяет эффективно балансировать нагрузку на сеть серверов. Использование иерархических слоев видеокадров существенно снижает задержки при передаче медиаданных клиентам с нестабильным интернет-соединением. Эти принципы адаптивного управления трафиком целесообразно учесть при разработке архитектуры. В результате общее качество обслуживания конечных пользователей значительно повысится.
1.2.2 Способ и устройство для представления подсказки причины сбоя видеозвонка
В данной работе был найден патент. Номер заявки 2010112919, дата подачи 02.04.2010 года. Выдан патент № 2 449 477. На данный патент имеет право ХУАВЭЙ ТЕКНОЛОДЖИЗ КО., ЛТД. (Китай). Автор изобретения: ХУАН Хой (CN). МПК: G08B 29/00 (2006.01). Дата публикации заявки: 10.10.2011, Бюл. № 28.
Изобретение относится к области телекоммуникаций и направлено на информирование вызывающего абонента о причинах сбоя при установлении видеозвонка. Способ предусматривает получение субъектом сетевой стороны значения причины сбоя видеозвонка, определенного исходным коммутатором, с которым сообщается вызывающий терминал. На основании сохраненного соответствия между кодами причин сбоев и текстовыми подсказками субъект сетевой стороны определяет и передает вызывающему терминалу информативное сообщение о причине неудачного вызова. Устройство содержит блок приема сообщения, блок поиска информации и блок представления подсказки. Система поддерживает динамическое обновление справочника кодов причин сбоев, а также получение обратной связи от пользователя после отображения подсказки. Изобретение реализовано в телефонных сетях с коммутацией каналов (передача кодов через сообщение IAM протокола ОКС-7).
1.3 Постановка задачи
На основе проведенного анализа существующих аналогов можно выделить ключевые элементы, которые нужно учитывать при разработке веб-приложения. В системе должно быть четыре основные роли: гость, пользователь, модератор и администратор. Для пользователя приложение должно реализовывать функции создания личных и групповых чатов, отправки текстовых сообщений и файлов, управления списком друзей, а также участия в голосовых и видеозвонках. Модератор должен иметь возможность удалять сообщения, исключать участников из групповых чатов и обрабатывать жалобы пользователей. Администратор должен иметь полный доступ к управлению пользователями системы: назначать роли, блокировать нарушителей, просматривать отчеты о нарушениях и выносить предупреждения. Такое четкое разделение полномочий необходимо для обеспечения высокого уровня безопасности и поддержания стабильной, комфортной среды общения на платформе. Это также значительно упростит техническую поддержку проекта.
Целью дипломного проекта является разработка веб-приложения «Lume» для видео-звонков.
Должны быть выполнены следующие требования:
– приложение должно поддерживать четыре роли: Гость, Пользователь, Модератор, Администратор;
– пользователь с ролью «Гость» должен иметь функционал регистрации с подтверждением по почте, авторизации с использованием JWT-токенов, восстановления пароля;
– пользователь с ролью «Пользователь» должен иметь возможность создавать и управлять личными и групповыми чатами, отправлять, редактировать и удалять сообщений, пересылать сообщения, искать сообщения в чате, управлять личным списком друзей, персонализировать профиль, совершать голосовые и видеозвонки;
– пользователь с ролью «Модератор» должен обладать возможностью выполнять поиск и просмотр пользователей, выдавать предупреждения с указанием причины, блокировать и разблокировать пользователей, просматривать жалобы на сообщения, закрывать жалобы;
– пользователю с ролью «Администратор» должен быть доступен функционал управления пользователями, управления чатами, рассылки сообщений всем пользователям системы;
– приложение должно содержать модуль статистики с отображением общего числа зарегистрированных пользователей, количества чатов, отправленных сообщений и журнала событий приложения.

2.1 Выбор средств реализации
Для разработки веб-приложения для видеозвонков и обмена сообщениями был тщательно подобран оптимальный стек технологий, обеспечивающий высокую производительность при обработке потоковых данных, устойчивая безопасность и возможность масштабирования системы в реальном времени. Основными критериями выбора стали поддержка асинхронного ввода-вывода, наличие развитой экосистемы для работы с WebRTC [5] и WebSocket [6], а также строгая типизация кода.
В качестве основы бэкенда выбрана программная платформа Node.js [7]. Это событийно-ориентированная среда выполнения, которая использует неблокирующую модель ввода-вывода, что делает ее идеальным решением для приложений реального времени с высокой интенсивностью обмена данными. Веб-сервер реализован с использованием фреймворка Express, который предоставляет гибкие инструменты для маршрутизации и обработки HTTP-запросов. Для организации стабильного двустороннего канала связи используется библиотека Socket.io.
Для создания динамичного и отзывчивого одностраничного интерфейса (SPA) выбрана популярная библиотека React [8]. Логика приложения реализована на языке TypeScript [9], использование которого позволяет выявлять ошибки на этапе компиляции и делает кодовую базу более предсказуемой и удобной для поддержки.
В качестве основной базы данных используется мощная объектно-реляционная СУБД PostgreSQL [10]. Она обеспечивает надежное хранение структурированной информации о пользователях, чатах и правах доступа. Взаимодействие с базой данных реализовано с помощью драйвера node-postgres (pg) [11], что позволяет выполнять оптимизированные SQL-запросы. Дополнительно для хранения неструктурированных данных (статических медиафайлов, таких как аватары пользователей) используется S3-совместимое объектное хранилище MinIO [12].
2.1.1 Серверная часть
Для реализации серверной части приложения выбрана программная платформа Node.js. Это событийно-ориентированная среда выполнения, построенная на движке V8, которая использует неблокирующую модель ввода-вывода. Такой выбор обусловлен необходимостью поддерживать большое количество одновременных подключений для работы чатов.
В качестве основного веб-фреймворка используется Express [13]. Это гибкий и минималистичный фреймворк для Node.js, предоставляющий надежный набор функций для построения современных масштабируемых одностраничных и многостраничных веб-приложений, а также гибридных веб-приложений. Он отвечает за маршрутизацию HTTP-запросов и организацию промежуточного программного обеспечения (middleware).
Основным языком разработки серверной части является TypeScript. Он добавляет строгую статическую типизацию к JavaScript [14], что позволяет выявлять ошибки на этапе компиляции, улучшает читаемость кода и упрощает рефакторинг сложных модулей бизнес-логики (контроллеров и сервисов).
Ключевым компонентом для реализации коммуникации в реальном времени является библиотека Socket.io [15]. Она обеспечивает двусторонний канал связи между клиентом и сервером с низкой задержкой, используя протокол WebSocket с возможностью автоматического переключения на Long Polling [16] при необходимости.
Для обеспечения безопасности и управления доступом применяется механизм аутентификации на основе JSON Web Tokens (JWT) [17]. Хеширование паролей пользователей осуществляется с помощью библиотеки bcryptjs [18], что гарантирует защиту учетных данных.
2.1.2 Клиентская часть
Разработка клиентского интерфейса ведется с использованием библиотеки React, обеспечивающей создание современного интерактивного одностраничного приложения. Выбор данной технологии обусловлен компонентным подходом, который позволяет разбивать сложный интерфейс на независимые переиспользуемые модули.
Логика клиентской части, как и серверной, реализована на языке TypeScript. Это обеспечивает сквозную типобезопасность и согласованность структур данных между фронтендом и бэкендом.
Архитектура приложения построена на использовании функциональных компонентов и хуков. Для эффективного управления глобальным состоянием (авторизация, активный звонок, список чатов) активно используется Context API [19], что позволяет избежать проблемы «prop drilling» и обеспечивает предсказуемый поток данных.
Взаимодействие с серверным API для операций CRUD организовано через HTTP-клиент Axios [20]. Для обмена сообщениями и сигнальными данными WebRTC используется клиентская библиотека socket.io-client. Визуальная составляющая реализована с использованием кастомных CSS-стилей, что обеспечивает уникальный дизайн и легковесность интерфейса.
2.1.3 База данных и хранилище
Для надежного хранения структурированных данных выбрана объектно-реляционная система управления базами данных PostgreSQL. Она отличается высокой производительностью, соответствием стандартам ACID и поддержкой сложных запросов. В рамках проекта PostgreSQL используется для хранения профилей пользователей, списков контактов, метаданных чатов и истории текстовых сообщений. Взаимодействие осуществляется через драйвер pg, что позволяет выполнять оптимизированные SQL-запросы напрямую.
Для хранения неструктурированных данных, таких как изображения профилей, используется объектное хранилище MinIO. Это высокопроизводительное S3-совместимое решение позволяет отделить статический контент от основной базы данных, снижая нагрузку на нее и упрощая масштабирование системы хранения медиафайлов.
2.2 Диаграмма вариантов использования
Диаграмма вариантов использования служит важным инструментом для визуализации функциональности веб-приложения, отображая ключевые взаимодействия между пользователями и системой. Она помогает четко определить роли и их задачи, обеспечивая понимание структуры приложения. На диаграмме вариантов использования представлены основные сценарии взаимодействия для разрабатываемой системы обмена сообщениями. Приложение поддерживает четыре основные роли: гость, пользователь, модератор и администратор. Каждая роль наделена определенными задачами и полномочиями, что обеспечивает гибкость и безопасность системы.
Роль гостя представляет неавторизованного посетителя приложения. В целях обеспечения конфиденциальности и безопасности данных, набор функций для этой роли строго ограничен. Гостю доступны базовые процессы аутентификации: регистрация новой учетной записи с вводом необходимых данных и авторизация в системе для получения токена доступа. Это является входной точкой для начала работы с приложением.
Пользователь является основным фактором, взаимодействующим с системой для коммуникации. После успешной авторизации ему предоставляется доступ к личному кабинету и основному функционалу мессенджера. Пользователь может осуществлять поиск других участников системы, отправлять и принимать заявки в друзья. Ключевой функционал включает обмен текстовыми сообщениями, создание групповых чатов, а также совершение аудио- и видеозвонков посредством технологии WebRTC. В личном профиле пользователю доступны возможности редактирования учетных данных, включая загрузку аватара (с сохранением в объектное хранилище) и смену пароля.
Роль модератора предполагает наличие специализированных прав для поддержания порядка в коммуникационной среде. Модератор имеет доступ к интерфейсу обработки жалоб (репортов), поступающих от пользователей. В его полномочия входит рассмотрение конфликтных ситуаций, вынесение предупреждений нарушителям правил сообщества, а также временное ограничение возможности отправки сообщений (mute) для конкретных пользователей. Данная роль необходима для обеспечения комфортной и безопасной атмосферы общения. Наличие данных эффективных инструментов позволяет модератору системы оперативно реагировать на любые инциденты и пресекать распространение нежелательного контента, минимизируя его негативное влияние на обычных пользователей.
Роль администратора наделена максимальными полномочиями для глобального управления всей системой. Он отвечает за полный контроль над учетными записями, включая просмотр полного списка пользователей и их блокировку в случае серьезных нарушений. Администратору доступна панель мониторинга с системной статистикой, позволяющая оценивать активность приложения. Кроме того, важной функцией является возможность отправки массовых системных уведомлений всем пользователям сервиса для информирования о технических работах или обновлениях.

2.3 Архитектура веб-приложения
Проект реализует современную архитектуру веб-приложения, разделенную на клиентскую и серверную части. Клиентская часть разработана как Single Page Application с использованием библиотеки React и языка TypeScript. Это обеспечивает создание динамичного и отзывчивого пользовательского интерфейса, который загружается один раз и работает непосредственно в браузере пользователя, минимизируя трафик.
Серверная часть выступает в роли основного узла обработки данных: она принимает API-запросы, выполняет аутентификацию пользователей, управляет бизнес-логикой и обеспечивает сигнализацию для соединения клиентов друг с другом. Реализация сервера выполнена на платформе Node.js с использованием фреймворка Express.
Для обеспечения высококачественной видео- и аудиосвязи в архитектуру интегрирована технология WebRTC. В отличие от традиционного клиент-серверного взаимодействия, медиаданные передаются напрямую между устройствами пользователей, что существенно снижает сетевую задержку и нагрузку на центральный узел. Сервер в данном процессе задействован исключительно на этапе установки связи – для обмена сигнальными данными, после чего клиенты поддерживают независимый и защищенный медиапоток.
Для обеспечения отказоустойчивости, удобства развертывания и независимости компонентов друг от друга в проекте применяется технология контейнеризации на базе Docker. Все ключевые узлы системы – серверное приложение, клиентская часть, СУБД PostgreSQL и объектное хранилище MinIO – функционируют в изолированных контейнерах, конфигурация которых централизованно управляется посредством Docker Compose, чтопозволяет разворачивать всё веб-приложение. Маршрутизация входящего трафика организована через веб-сервер Nginx, который выступает в роли обратного прокси-сервера. Он распределяет запросы между внутренними сервисами и отвечает за терминацию SSL/TLS-соединений, гарантируя безопасность передаваемых по сети данных.

Центральный сервер приложений Node.js принимает все входящие запросы от пользователя напрямую. Обработка данных распределена между двумя хранилищами: реляционной базой данных PostgreSQL для хранения учетных записей и текстовой информации, и объектным хранилищем MinIO для размещения статических медиафайлов.
Все сетевые запросы между компонентами приложения происходят по стандартным протоколам:
HTTP/HTTPS – для обмена данными между клиентом и сервером;
WebSocket – для обеспечения двусторонней связи в реальном времени;
TCP – для обеспечения надежного взаимодействия сервера с базой данных и файловым хранилищем.
Такая архитектура позволяет обеспечить быструю обработку запросов за счет асинхронной модели ввода-вывода Node.js, улучшает производительность системы и упрощает масштабируемость отдельных сервисов.

Проектирование базы данных включает 22 таблицы, связанных между собой посредством внешних ключей. Данная структура обеспечивает целостность данных, поддерживает разделение прав доступа через ролевую модель на двух уровнях (глобальные роли и роли внутри чатов) и позволяет эффективно хранить историю коммуникации, реакции, опросы, упоминания, подтверждения прочтения, голосования и действия модерации.
Базу данных можно разделить на четыре логические группы: основные таблицы, таблицы коммуникации, таблицы модерации и служебные таблицы.
Основные таблицы составляют ядро системы. Таблица «roles» является справочником и хранит три предустановленные роли. Таблица «users» ссылается на «roles» по внешнему ключу role_id, что обеспечивает глобальное разграничение прав доступа. Таблица «user_profiles» реализует связь один-к-одному с «users» и хранит исключительно косметические данные профиля – цвета, бейдж, фон, страну и биографию – вынесенные в отдельную таблицу в соответствии с третьей нормальной формой. Таблица «chats» описывает все чаты системы – как личные (один на один), так и групповые, различаемые флагом is_group. Связующая таблица «chat_users» реализует связь «многие-ко-многим» между «users» и «chats», а поле chat_role с ограничением CHECK обеспечивает второй уровень разграничения прав – внутри конкретного чата (member, moderator, trusted). Владелец чата определяется через поле creator_id в таблице «chats». Таблица «friends» реализует двустороннюю связь между пользователями со статусной моделью (pending → accepted), при этом ограничение UNIQUE(user_id, friend_id) исключает дублирование заявок.
Для всех сущностей ядра системы спроектирована строгая ссылочная целостность с использованием ограничений ON DELETE CASCADE для зависимых профилей и связующих таблиц. Это гарантирует автоматическую очистку смежных записей при удалении пользователя или чата, предотвращая появление изолированных строк и аномалий данных. Использование суррогатных первичных ключей типа SERIAL в основных таблицах оптимизирует индексацию и ускоряет выполнение операций соединения JOIN при построении сложных выборок.
Таблицы коммуникации обеспечивают функциональность обмена сообщениями. Центральной является таблица «messages», связанная с «chats» через chat_id и с «users» через sender_id. Сообщения поддерживают ответы (самореференция через reply_to_id), пересылку (forwarded_from_id), редактирование (edited_at) и эфемерность (expires_at). Таблица «message_deleted_for» реализует механизм мягкого удаления сообщений для отдельных пользователей: вместо массива в колонке сообщения используется отдельная таблица с составным первичным ключом, что соответствует первой нормальной форме. Таблица «message_reactions» обеспечивает систему реакций с ограничением уникальности по комбинации сообщение–пользователь–эмодзи. Таблица «message_mentions» фиксирует упоминания пользователей через символ @ с отслеживанием факта просмотра; поле chat_id намеренно исключено, так как оно транзитивно определяется через message_id, что соответствует третьей нормальной форме. Таблица «message_reads» фиксирует факт прочтения каждого отдельного сообщения конкретным пользователем. Таблицы «chat_read_status» и «message_reads» реализуют двухуровневую систему подтверждений прочтения: первая отслеживает общий прогресс чтения чата, вторая – факт прочтения каждого отдельного сообщения. Таблица «pinned_messages» связывает чат и сообщение для функции закрепления с ограничением уникальности по паре (chat_id, message_id). Таблица «scheduled_messages» хранит отложенные сообщения с привязкой ко времени отправки и флагом отправки sent. Таблица «polls» привязана одновременно к чату, создателю и сообщению-контейнеру. Варианты ответов хранятся в отдельной таблице «poll_options», а голоса – в отдельной таблице «poll_votes» с составным первичным ключом (poll_id, user_id), что исключает повторное голосование и устраняет гонку данных, которая возникала бы при хранении голосов в формате JSONB.
Таблицы модерации обеспечивают контроль за соблюдением правил платформы. Таблица «reports» связана с «users» через два внешних ключа – reporter_id (автор жалобы) и reported_user_id (нарушитель) – а также с «messages» через message_id, и содержит статусную модель обработки с ограничением CHECK (pending, resolved, dismissed). Таблица «warnings» фиксирует предупреждения с указанием модератора, выдавшего предупреждение, и причины его выдачи.
Служебные таблицы не связаны с основной бизнес-логикой напрямую. Таблицы «registration_codes» и «password_reset_codes» хранят временные данные для процедур регистрации и восстановления пароля соответственно – записи в них автоматически удаляются по истечении одного часа и пятнадцати минут соответственно посредством планировщика на стороне сервера. Таблица «app_logs» является автономной, не содержит внешних ключей и хранит системные логи с уровнем, текстом сообщения и мета-данными в формате JSONB для мониторинга и диагностики.
Все связи между таблицами реализованы через внешние ключи с каскадным удалением для зависимых данных и обнулением для справочных ссылок, что обеспечивает ссылочную целостность базы данных при любых операциях удаления. Такая конфигурация минимизирует риск появления лишних записей и избавляет разработчиков от необходимости вручную очищать таблицы.
2.5 Проектирование основных алгоритмов
2.5.1 Алгоритм отправки личного сообщения
Процесс отправки сообщения начинается с того, что пользователь открывает диалоговое окно с выбранным собеседником, где может ввести текст или прикрепить медиафайл. Для выполнения операции необходима авторизация: если токен доступа отсутствует или истек, система блокирует попытку и перенаправляет пользователя на страницу входа.
Когда авторизованный пользователь нажимает кнопку отправки, клиентское приложение формирует запрос. На стороне сервера первым этапом выполняется проверка валидности JWT-токена и статуса отправителя: система удостоверяется, что пользователь не находится в глобальном черном списке сервиса. Если пользователь заблокирован администратором, обработка запроса прекращается с возвратом ошибки доступа.
Далее инициируется проверка прав на взаимодействие: сервер обращается к базе данных, чтобы убедиться, что получатель сообщения существует, и между пользователями установлена связь. Дополнительно проверяется черный список самого получателя: если отправитель был заблокирован собеседником персонально, доставка сообщения невозможна.
В случае наличия вложений запускается подпроцесс работы с объектным хранилищем MinIO. Файл валидируется по типу и размеру, загружается в хранилище, после чего генерируется уникальная ссылка для доступа к ресурсу. Если все проверки пройдены успешно, система сохраняет запись о сообщении в базе данных PostgreSQL.
Финальным этапом является маршрутизация через websocket: сервер определяет, находится ли получатель в сети. Если соединение активно, сообщение доставляется мгновенно через событийную модель socket.io, обновляя интерфейс получателя без перезагрузки страницы. В случае отсутствия адресата в сети сообщение сохраняется в истории со статусом непрочитанного и доставляется сразу после его авторизации. Это обеспечивает гарантированную синхронизацию переписки и корректное отображение счетчика уведомлений на клиенте. Схема алгоритма отправки сообщения представлена в приложении Г.
2.5.2 Алгоритм оптимизации видеозвонка
Процесс оптимизации качества видеосвязи начинается параллельно с установлением WebRTC-соединения между пользователями и активацией передачи видеопотока. Система инициирует асинхронный сбор сетевой статистики с интервалом по умолчанию в 200 миллисекунд. На этом этапе из отчетов о статистике соединения извлекаются ключевые метрики реального времени: время кругового пути, джиттер (колебание задержки), уровень потери пакетов и доступная исходящая пропускная способность.
Для обеспечения точности прогнозирования собранные данные сохраняются в «скользящем окне», которое хранит историю сетевых метрик за последние 30 секунд, автоматически удаляя устаревшие записи. Далее система вычисляет прогноз состояния сети на 2 секунды вперед, используя данные за последние 5 секунд. Вычисление производится с помощью гибридной математической модели, которая усредняет результаты двух алгоритмов: двойного экспоненциального сглаживания Хольта (DES) и взвешенной линейной регрессии. Метод Хольта позволяет быстро реагировать на внезапные скачки и падения качества, а метод регрессии, где более свежие данные имеют экспоненциально больший вес, оценивает долгосрочную тенденцию.
Полученные в результате экстраполяции прогнозируемые значения сопоставляются с жесткими критическими порогами: RTT свыше 300 мс, потеря пакетов более 5% или джиттер больше 50 мс. Если алгоритм предсказывает превышение хотя бы одного из этих порогов, фиксируется ожидаемая деградация сети. В этом случае алгоритм немедленно производит троттлинг: параметры видеокодека обновляются, принудительно снижая максимальный исходящий битрейт видео до 500 кбит/с, чтобы предотвратить потерю соединения и обеспечить непрерывность связи.
Финальным этапом алгоритма является механизм восстановления качества. Если алгоритм больше не прогнозирует деградацию, система переходит в режим восстановления. Битрейт не возвращается к максимуму мгновенно, чтобы не спровоцировать новый сбой; вместо этого он плавно повышается с шагом в 200 кбит/с каждые 2 секунды. Параллельно с этим на каждом шаге итерации система производит контрольный замер уровня задержки (ping) и процента потери пакетов (packet loss), чтобы убедиться, что сетевой канал успешно справляется с возрастающей нагрузкой. Такой итеративный подход минимизирует риски возникновения колебаний качества, стабилизирует нагрузку на процессор устройства и обеспечивает максимально плавный переход между различными разрешениями видеопотока без видимых для пользователя фризов. Процесс постепенного повышения продолжается до тех пор, пока пропускная способность не достигнет оптимального целевого значения в 2.5 Мбит/с (нормальное качество), после чего система возвращается в стандартный режим мониторинга. Схема алгоритма оптимизации видеозвонка представлена в приложении Д.
2.5.3 Алгоритм создания группового чата
Чтобы создать отдельный новый групповой чат, пользователь с самого начала взаимодействует с графическим интерфейсом (GUI), где вводит необходимое название новой создаваемой комнаты в отдельном модальном окне и отправляет соответствующий запрос. После этого данные мгновенно передаются в серверный блок обработки (API), который выполняет необходимую первичную валидацию (например, проверку на то, что название не является пустым) и направляет информацию по порядку дальше, в отдельный специальный сервис управления чатами. Этот сервис, в свою очередь, генерирует уникальный код приглашения, привязывает чат к идентификатору создателя и обращается к базе данных, чтобы записать новую сущность в соответствующую таблицу. Если во время выполнения возникает ошибка, например, при провале валидации некорректных данных, система немедленно формирует ответ с ошибкой (со статус-кодом 400), который возвращается из блока обработки обратно в графический интерфейс, где пользователю визуально отображается динамически всплывающее уведомление об ошибке. Если операция проходит успешно, база данных сохраняет новый чат, сервис получает подтверждение и передает данные созданной модели обратно через цепочку: сначала в блок обработки (API), затем в GUI, где список чатов пользователя обновляется и выводится уведомление об успешном создании. Диаграмма последовательности данного алгоритма представлена в приложении Е.
Данная схема наглядно отражает последовательность взаимодействия между всеми клиентскими и серверными компонентами системы при создании пользовательского группового чата, обеспечивая целостность бизнес-логики и корректность внесения данных.
2.6 Выводы по разделу
Разрабатываемое веб-приложение для обмена сообщениями представляет собой комплексную платформу, сочетающую в себе передовые технологии и современные архитектурные подходы. Использование клиент-серверной архитектуры, реализованной с применением Node.js и Express для создания производительной серверной части, React для разработки динамичного SPA-интерфейса, и связки PostgreSQL с MinIO для надежного хранения структурированных и неструктурированных данных, обеспечивает высокую скорость работы, гибкость и масштабируемость всей системы.
Спроектированный технологический стек позволяет пользователям обмениваться текстовыми сообщениями и файлами в реальном времени, управлять списком контактов и совершать видеозвонки через WebRTC, а модераторам – эффективно отслеживать нарушения и реагировать на жалобы. Администраторы, в свою очередь, получают полный контроль над безопасностью системы: от управления ролями и правами доступа до мониторинга активности и глобальной блокировки нарушителей.
Проектирование реляционной базы данных обеспечивает устойчивую логическую структуру для хранения профилей, социальных связей, истории переписки и логов модерации. Использование механизмов каскадного удаления и внешних ключей дополнительно исключает появление изолированных записей при удалении аккаунтов или чатов.
Важным аспектом архитектурной устойчивости является внедрение механизмов автоматической обработки разрывов соединений и синхронизации состояний. Благодаря интеграции Socket.io, приложение реализует систему подтверждения доставки (acknowledgments), что исключает потерю сообщений при кратковременных сбоях сети. Логика работы фронтенд-части на базе React дополнена эффективным управлением состоянием, что позволяет мгновенно обновлять интерфейс (оптимистичное обновление) еще до получения подтверждения от сервера, создавая ощущение бесшовной работы и высокого отклика системы.
Особое внимание в проекте уделено обеспечению безопасности и конфиденциальности пользовательских данных. Реализованная система аутентификации на базе стандартов JWT (JSON Web Tokens) с использованием пар access и refresh токенов гарантирует надежную защиту сессий и предотвращает несанкционированный доступ к API. Хеширование паролей с применением криптографической библиотеки bcryptjs исключает возможность утечки учетных данных в открытом виде.
Параллельно с этим, интеграция объектного хранилища MinIO позволила вынести тяжеловесный контент за пределы основной базы данных, что радикально снизило нагрузку на дисковую подсистему PostgreSQL. Использование S3-совместимого API обеспечивает быстрый доступ к медиафайлам и документам, а также упрощает процедуру резервного копирования и восстановления данных. Разделение потоков обработки текстовых данных и бинарных объектов не только оптимизирует потребление ресурсов сервера, но и закладывает основу для внедрения CDN-решений в будущем, что позволит масштабировать доставку контента на глобальном уровне без перепроектирования ядра системы.
Для упрощения процессов развертывания и администрирования программного комплекса применена технология контейнеризации Docker. Изоляция компонентов системы – сервера приложений, базы данных PostgreSQL и объектного хранилища MinIO – в отдельные контейнеры обеспечивает предсказуемость среды выполнения и исключает конфликты зависимостей.

3.1 Обзор технологий реализации веб-приложения
В качестве языка программирования для серверной части был выбран TypeScript поверх среды выполнения Node.js. Node.js – это асинхронная, событийно-ориентированная среда, позволяющая обрабатывать большое количество одновременных соединений. Благодаря неблокирующей архитектуре Node.js подходит для высоконагруженных веб-приложений и API реального времени.
TypeScript – строго типизированный надмножество JavaScript, разработанное Microsoft. Использование TypeScript позволяет выявлять ошибки еще на этапе компиляции, улучшает читаемость кода, а также предоставляет развитую поддержку IDE через автодополнение и проверку типов.
Фреймворком для создания API был выбран Express.js – минималистичный и гибкий веб-фреймворк для Node.js. Express предоставляет мощные инструменты для маршрутизации, обработки HTTP-запросов, middleware-функций и быстрого создания RESTful API. Он широко используется в индустрии благодаря своей простоте, расширяемости и активному сообществу.
Для обеспечения обмена сообщениями в реальном времени используется библиотека Socket.io – надстройка над WebSocket-протоколом для Node.js. Socket.io автоматически выбирает оптимальный транспорт и предоставляет механизм комнат, что позволяет организовать адресную рассылку событий между пользователями и чатами.
Для клиентской части приложения выбрана современная популярная библиотека React 19 – библиотека JavaScript, разработанная Meta для создания пользовательских интерфейсов.
Tailwind CSS – утилитарный CSS-фреймворк для быстрой верстки ин-терфейсов. Позволяет создавать уникальные дизайны через комбинацию готовых классов без написания отдельных CSS-файлов. В проекте используется расширенная палитра, задающая цветовую схему приложения.
Docker – инструмент контейнеризации для развертывания приложений в изолированной среде. Обеспечивает стабильность и воспроизводимость окружения на любой операционной системе с установленным Docker.
Docker Compose – инструмент для управления многоконтейнерными приложениями. Упрощает настройку и совместный запуск сервисов базы данных, серверной и клиентской частей приложения.
JSON Web Token (JWT) – открытый стандарт для создания токенов доступа, подтверждающих набор утверждений. В проекте используется дляаутентификации пользователей и авторизации соединений Socket.io.
Multer – middleware для Node.js, обеспечивающее обработку загружаемых файлов в формате multipart/form-data. Используется для приема аватарови медиафайлов от клиентов.
MinIO SDK – клиентская библиотека для объектного хранилища, со-вместимого с Amazon S3 API. В проекте применяется для загрузки файлов в Cloudflare R2 и формирования публичных URL.
Для управления зависимостями используется менеджер пакетов npm –стандартный менеджер пакетов, входящий в состав Node.js. Он упрощает процесс установки и обновления сторонних библиотек, а также управление зависимостями как в серверной, так и в клиентской части приложения.
3.2 Система управления базами данных PostgreSQL
В качестве базы данных используется PostgreSQL – мощная реляционная СУБД с открытым исходным кодом, поддерживающая сложные запросы, транзакции, индексы и расширенные типы данных. PostgreSQL хорошо интегрируется с Node.js через драйвер pg.
Для взаимодействия с базой данных в приложении используется пул соединений pg.Pool, настроенный в модуле databasepg.ts. В продуктивной средесоединение устанавливается по строке DATABASE_URL с включенным SSL; в среде разработки используются отдельные параметры подключения без SSL.
Схема базы данных создается при каждом запуске сервера посредством инструкций CREATE TABLE IF NOT EXISTS в файле index.ts. Такой подход обеспечивает идемпотентность: повторный запуск сервера не приводит к потере данных, а новые таблицы появляются автоматически. Изменения существующих столбцов применяются вручную или через пересоздание таблицы.
3.3 Взаимодействие с базой данных
В качестве базы данных используется PostgreSQL – мощная реляционная СУБД с открытым исходным кодом, поддерживающая сложные запросы, полное соответствие критериям ACID для обеспечения надежности транзакций, индексы и расширенные типы данных PostgreSQL хорошо интегрируется с Node.js через драйвер pg.
Для взаимодействия с базой данных в приложении используется пул соединений pg.Pool, настроенный в модуле databasepg.ts. В продуктивной средесоединение устанавливается по строке DATABASE_URL с включенным SSL; в среде разработки используются отдельные параметры подключения без SSL.
Схема базы данных создается при каждом запуске сервера посредством инструкций CREATE TABLE IF NOT EXISTS в файле index.ts. Изменения существующих столбцов применяются вручную или через пересоздание таблицы.
Для взаимодействия с PostgreSQL в приложении используется драйвер node-postgres. Все запросы к базе данных вынесены в слой сервисов (директория Services/), что обеспечивает разделение бизнес-логики и HTTP обработчиков. Пример конфигурации пула соединений представлен на листинге 3.1.
import { Pool } from 'pg';
const isProduction = !!process.env.DATABASE_URL;
export const pool = isProduction
? new Pool({
connectionString: process.env.DATABASE_URL,
ssl: { rejectUnauthorized: false },
})
: new Pool({
host: process.env.DB_HOST,
port: Number(process.env.DB_PORT) || 5432,
user: process.env.DB_USER,
password: process.env.DB_PASSWORD,
database: process.env.DB_DATABASE,
});

3.6 Реализация функциональности
В соответствии с диаграммой вариантов использования в коде реализованы функции, доступные пользователям с различными ролями: USER, MODERATOR и ADMIN.
3.6.1 Регистрация
Функция register предназначена для регистрации новых пользователей в системе. Перед созданием аккаунта проверяется наличие действующего кода подтверждения email в таблице registration_codes. Если код верен, создается запись в таблице users с захэшированным паролем (bcrypt) и ролью user. Функция возвращает пару токенов: access-токен (15 минут) и refresh-токен (30 дней), сохраняемый в таблице refresh_tokens.
Реализация регистрации с проверкой входных данных, хешированием пароля и отправкой кода подтверждения представлена в листинге Ж. В рамках данного процесса также инициализируется транзакция на уровне базы данных, что предотвращает появление частичных или некорректных записей в случае непредвиденного сбоя. Дополнительно система осуществляет автоматическую очистку устаревших одноразовых кодов из оперативной памяти для оптимизации хранения и предотвращения повторного использования компрометированных данных.
3.6.2 Авторизация
Функция login отвечает за процесс входа пользователя в систему. В качестве входных параметров метод принимает учетные данные пользователя, проходящие предварительную валидацию на стороне клиентского приложения для снижения нагрузки на сервер. Фрагмент реализации метода авторизации представлен на листинге 3.2, а полный код представлен в приложении Ж.

3.6.3 Получение истории сообщений
Функция getChatMessages предназначена для извлечения сообщений из базы данных с поддержкой вложенных данных: информации о отправителе, цитируемом сообщении (reply_to) и прикрепленных реакциях. Функция представлена на листинге 3.3 и приложении И.
export const getChatMessages = async (chatId: number, userId: number) => {
const { rows } = await pool.query(`SELECT m.*,
row_to_json(u) AS sender,
row_to_json(r) AS reply_to,
COALESCE(
json_agg(mr) FILTER (WHERE mr.id IS NOT NULL), '[]'
) AS reactions FROM messages m
JOIN users u ON u.id = m.sender_id
LEFT JOIN messages r ON r.id = m.reply_to_id
LEFT JOIN message_reactions mr ON mr.message_id = m.id
WHERE m.chat_id = $1
AND NOT ($2 = ANY(m.deleted_for))
GROUP BY m.id, u.id, r.id
ORDER BY m.created_at ASC`, [chatId, userId]); return rows;};
Листинг 3.3 – Получение истории сообщений с реакциями и цитатами
Если пользователь удалил сообщение «для себя», его идентификатор попадает в массив deleted_for, что позволяет системе автоматически исключать данную запись из выборки при каждом последующем запросе к истории чата.

3.6.6 Управление ролями в чате
Функция setChatMemberRole позволяет владельцу чата или глобальному администратору назначать участникам роли: member, moderator или trusted. Роль moderator дает право исключать участников и удалять сообщения; роль trusted – приглашать новых участников. Роль владельца не может быть изменена. Для обеспечения безопасности выполнение данной операции сопровождается строгой валидацией на уровне субд, исключающей возможность эскалации привилегий со стороны рядовых пользователей.

3.8 Реализация аутентификации Socket.io
При установке соединения Socket.io клиент передает access-токен в поле auth.token. Серверный middleware Socket.io верифицирует токен и прикрепляет идентификатор пользователя к объекту socket.data. Фрагмент серверной настройки показан в листинге 3.7.
io.use((socket, next) => {
const token = socket.handshake.auth?.token;
if (!token) return next(new Error('Unauthorized'));
try {
const payload = jwt.verify(token, process.env.JWT_SECRET!) as JwtPayload;
socket.data.userId = payload.id;
next();
} catch {
next(new Error('Invalid token'));
}
});

Использование механизма комнат позволяет эффективно абстрагироваться от управления конкретными идентификаторами сокетов, которые могут меняться при каждом переподключении клиента. Благодаря этому система осуществляет широковещательную рассылку сообщений на основе постоянного идентификатора чата.

3.9.1 Управление состоянием через контексты React
Для управления глобальным состоянием приложения используется встроенный Context API React. Иерархия провайдеров в App.tsx выглядит следующим образом: AuthProvider, SocketProvider, ChatProvider, CallProvider.
AuthContext хранит текущего пользователя, access- и refresh-токены, а также предоставляет функции login, logout и updateUser. SocketContext создает устойчивое дуплексное соединение socket.io-client после успешной аутентификации и показывает баннер «Нет соединения» при обрыве связи. CallContext реализует WebRTC-сигналинг для голосовых и видеозвонков. Полный код функционала представлен в приложении Л.
3.9.2 HTTP-взаимодействие с сервером
Для выполнения HTTP-запросов к серверному API используется единый Axios-инстанс, настроенный в /api.tsx. Если обновление токена в данный момент невозможно, пользователь автоматически выходит из системы. Пример вызова показан в листинге 3.8. Этот механизм обеспечивает бесшовный пользовательский опыт, так как авторизация поддерживается в актуальном состоянии в фоновом режиме без необходимости повторного ручного ввода логина и пароля.
const api = axios.create({ baseURL: process.env.REACT_APP_API_URL });
api.interceptors.response.use(
(response) => response, async (error) => {
if (error.response?.status === 401 && !error.config._retry){
error.config._retry = true;
const { data } = await axios.post('/auth/refresh', { refreshToken });
localStorage.setItem('token', data.accessToken);
error.config.headers['Authorization'] = `Bearer ${data.accessToken}`;
return api(error.config);}
return Promise.reject(error);});

Внедрение индексов по ключевым полям (таким как идентификаторы пользователей и чатов), а также оптимизация структуры таблиц позволили сохранить минимальное время отклика (микросекундный диапазон) бэкенда при обработке запросов к переписке даже в условиях интенсивного роста объема хранимых данных.

4.1 Негативное тестирование формы входа
Для обеспечения комплексной проверки веб-приложения применяются различные виды тестирования: функциональное, проверяющее выполнение системой своих прямых задач (отправка сообщений, регистрация), и нефункциональное, оценивающее такие характеристики, как производительность и безопасность. Особое место занимает негативное тестирование, которое направлено на проверку устойчивости приложения к некорректным действиям пользователя или сбоям внешних систем. Использование сценариев, соответствующих непредвиденному поведению тестируемой системы, позволяет убедиться, что приложение не «упадет» при ошибке, а корректно обработает ее и выведет соответствующее уведомление.
На экране входа присутствуют поля для ввода имени пользователя и пароля, а также кнопка «Войти». Начнем тестирование, оставив поле пароля пустым. В соответствии с ожиданиями, что представлено на рисунке 4.1, кнопка «Войти» не активна, пока хотя бы одно из полей пустое или содержит только пробелы – это проверяется на клиентской стороне в специальном обработчике события отправки формы.
Рисунок 4.1 – Отсутствие имени пользователя и пароля при входе
Как показано на рисунке 4.2, при вводе имени пользователя, которое не зарегистрировано в системе, сервер возвращает ответ с кодом 400 и сообщение «Пользователь с таким именем не найден».
Такое визуальное подтверждение демонстрирует корректную работу фронтенд-части по интерпретации ошибок сервера, при которой валидационное сообщение выводится непосредственно в интерфейсе формы, мгновенно информируя пользователя о необходимости проверки введенных данных.

Таким образом, реализованная логика аутентификации соответствует современным требованиям безопасности и обеспечивает стабильную работу приложения в условиях эксплуатации.

Рисунок 4.7 – Валидирование поля пароля
Для поля имени пользователя проверяется длина (от 2 до 32 символов). При нарушении ограничений сервер возвращает понятное описание ошибки.

Использование уникальных индексов в базе данных в сочетании с этой проверкой гарантирует чистоту пользовательских данных и предотвращает конфликты идентификации внутри системы.
Рисунок 4.9 – Проверка на совпадение нового пользователя

4.4 Негативное тестирование функций администрирования
При попытке обратиться к маршрутам /admin/* без токена или с токеном пользователя, не имеющего роли ADMIN, сервер возвращает ответ 403. Аналогично при обращении к маршрутам /moderator/* без роли MODERATOR или ADMIN возвращается ответ 403.
Промежуточный обработчик roleMiddleware проверяет роль пользователя при каждом запросе путем чтения актуального значения из базы данных, а не из токена. Это исключает использование устаревшего токена для получения повышенных привилегий после понижения роли.
При попытке заблокировать другого модератора или администратора сервер возвращает ответ 403 с сообщением «Нельзя забанить администратора или модератора», что показано на рисунке 4.17.

Такое ограничение встроено в реализованную бизнес-логику сервера как критическая мера безопасности, исключающая возможность захвата контроля над платформой через компрометацию или иные неправомерные действия одного из модераторов.

После заполнения формы пользователь нажимает кнопку перехода к следующему шагу. Если данные введены корректно, система отправляет код подтверждения на указанный адрес электронной почты. Форма регистрации представлена на рисунке 5.2.

Все действия с перепиской, включая добавление эмодзи-реакций, изменение или удаление текста, мгновенно синхронизируются между экранами обоих собеседников за счет использования протокола WebSocket.

После подтверждения названия групповой чат создается и автоматически открывается в основной области. Создатель чата получает права управления участниками и может приглашать других пользователей. Интерфейс создания группового чата представлен на рисунке 5.10.

Во время набора текста остальные участники чата видят индикатор активности. После отправки сообщение появляется в истории переписки. Если сообщение было отправлено пользователем, оно отображается справа, сообщения других участников отображаются слева. Отправка текстового сообщения представлена на рисунке 5.13.

После загрузки файл отображается в переписке в виде карточки, изображения, видео или иного другого доступного элемента.
Для отправки эмодзи или стикера необходимо открыть панель медиаэлементов и выбрать необходимую соответствующую вкладку. Выбранный эмодзи добавляется в текст сообщения, а стикер отправляется как отдельное сообщение. Как показано на рисунке 5.14, интерфейс работы с мультимедийными вложениями обеспечивает удобный предварительный просмотр выбранных файлов перед их окончательной отправкой, что минимизирует риск загрузки ошибочных данных. интегрированный модуль предварительного просмотра поддерживает динамическое отображение графических изображений, видеофрагментов и документов популярных форматов.

Также в приложении доступна отправка видеозаметок. Для этого пользователь нажимает кнопку записи видеосообщения, записывает короткий видеоролик и отправляет его в чат. Для администратора описаны функции управления пользователями, изменения ролей, удаления учетных записей, просмотра и удаления чатов, выполнения системной рассылки, анализа статистики и просмотра журналов событий. 6.1 Общая характеристика разрабатываемого программного средства
Веб-приложение представляет собой программное обеспечение для личного и группового общения, обмена файлами, проведения аудио и видеозвонков и взаимодействия пользователей в режиме реального времени. Приложение ориентировано на небольшие команды, учебные группы и онлайн-сообщества, которым требуется единая коммуникационная среда без установки отдельного клиентского приложения.
Пользователь может зарегистрироваться, настроить профиль, вести личные диалоги, создавать и использовать групповые чаты, отправлять сообщения и медиафайлы, применять реакции, опросы, закрепленные и отложенные сообщения, а также участвовать в звонках. Для администраторов и модераторов предусмотрены управление пользователями, чатами, жалобами и журналами событий.
Архитектура проекта включает клиентскую часть на React и TypeScript, серверную часть на Node.js и Express, базу данных PostgreSQL, обмен событиями через Socket.IO, подсистему аудио- и видеосвязи на базе mediasoup, хранение файлов и интеграции для субтитров и перевода сообщений.
По типу программных средств веб-приложение относится к коммуникационным веб-сервисам общего назначения. По степени сложности проект следует отнести к первой группе, поскольку он работает в режиме реального времени, обеспечивает телекоммуникационную обработку данных, аудио- и видеосвязь, интерактивное взаимодействие пользователей и графический вывод интерфейса. По степени новизны проект является развитием известного класса программных средств, так как на рынке существуют аналоги, однако сочетание браузерного доступа, модерации, персонализации, субтитров и функций реального времени формирует прикладные преимущества для выбранной аудитории.
В качестве способа монетизации принята продажа разработанного веб-приложения с передачей имущественных прав заказчику. После передачи прав заказчик получает возможность использовать, дорабатывать и коммерчески применять программное средство в своей деятельности.

6.3 Методика обоснования цены
Согласно методике экономического обоснования программных средств, завершенное программное средство рассматривается как научно-техническая продукция, имеющая функционально законченный вид. Экономический результат может проявляться у разработчика в форме прибыли от реализации или эксплуатации продукта, а у пользователя – в экономии времени, трудовых, материальных и финансовых ресурсов. При этом оценка эффективности программного обеспечения требует комплексного подхода, учитывающего как прямые первоначальные инвестиции, так и долгосрочные эксплуатационные затраты на поддержание инфраструктуры.
Экономический эффект разработчика связан с возможностью покрыть затраты и получить прибыль за счет продажи разработанного веб-приложения с передачей имущественных прав заказчику. Пользовательский эффект выражается в объединении нескольких коммуникационных инструментов в одном веб-сервисе: переписки, звонков, обмена файлами, групповых пространств и базовой модерации.
Стоимостная оценка проекта включает основную и дополнительную заработную плату исполнителей, отчисления на социальные нужды, материальные расходы, специальное оборудование и платные услуги, прочие прямые затраты, накладные расходы, сопровождение и адаптацию. После этого рассчитываются полная себестоимость, рыночная цена реализации, прибыль, рентабельность и чистая прибыль.
Поскольку программное средство передается заказчику с имущественными правами, основным источником экономического результата выступает единовременная цена реализации. Для обоснования данной цены затраты на разработку сопоставляются с рыночными оценками создания аналогичных веб-приложений.

async postMessage(req: Request, res: Response, next: NextFunction): Promise<void> {    try {      const authReq = req as AuthRequest;      const chatId = req.params.id as string;      const senderId = authReq.user?.id;      const { text, reply_to_id, expires_in_seconds } = req.body;      if (!senderId || !authReq.user) {          res.status(401).json({ message: "Пользователь не авторизован" });          return;      }      if (!text || typeof text !== "string" || !text.trim()) {        res.status(400).json({ message: "Текст сообщения не может быть пустым" });        return;      }      if (text.length > 10_000) {        res.status(400).json({ message: "Сообщение слишком длинное (максимум 10 000 символов)" });        return;      }      const msg = await chatService.postMessage(chatId, senderId, text, reply_to_id ?? null, expires_in_seconds ?? null);      const mentionRegex = /@(\w+)/g;      const mentionedUsernames: string[] = [];      let m;      while ((m = mentionRegex.exec(text)) !== null) {        mentionedUsernames.push(m[1]);      }      if (mentionedUsernames.length > 0) {        // Find mentioned users who are members of this chat        const usersRes = await client.query(          `SELECT u.id FROM users u           JOIN chat_users cu ON cu.user_id = u.id AND cu.chat_id = $1           WHERE u.username = ANY($2) AND u.id != $3`,          [chatId, mentionedUsernames, senderId]        );        for (const row of usersRes.rows) {          await client.query(            "INSERT INTO message_mentions (message_id, mentioned_user_id) VALUES ($1, $2) ON CONFLICT DO NOTHING",            [msg.id, row.id]          );          req.app.get("io").to(`user_${row.id}`).emit("mention_received", {            messageId: msg.id,            chatId: Number(chatId),            senderName: authReq.user.username,            text,          });        }      }      req.app.get("io").to(`chat_${chatId}`).emit("new_message", msg);      res.json(msg);    } catch (e) {      next(e);    }  }

function checkCallRateLimit(userId: number): boolean {  const now = Date.now();  const entry = callRateLimit.get(userId);  if (!entry || now > entry.resetAt) {    callRateLimit.set(userId, { count: 1, resetAt: now + 60_000 });    return true;  }  if (entry.count >= 5) return false;  entry.count++;  return true;}
